# 1모듈 · 에이전트와 실행 루프

> 예상 시간: 25~35분 · 선수 지식: Python 함수와 JSON 객체

## 학습 목표

이 모듈을 마치면 모델의 도구 호출 요청과 실제 도구 실행을 구분할 수 있다. 또한 에이전트가 어떤 근거로 다음 행동을 정하고 언제 멈춰야 하는지 설명할 수 있다.

## 실패 장면

Mori Shop 고객 `C-102`가 말했다.

> 지난주 받은 블루투스 이어폰을 환불해 줘.

단순한 챗봇은 다음처럼 답할 수 있다.

> O-1042 주문의 환불을 완료했습니다. 89,000원이 곧 입금됩니다.

문장은 자연스럽지만 확인된 사실은 하나도 없다. 챗봇은 고객의 주문을 조회하지 않았고, 환불 사유도 묻지 않았다. 환불 레코드 역시 만들지 않았다. “완료했다”는 문장과 외부 시스템의 실제 상태는 서로 다르다.

## 30초 핵심

에이전트는 다음 세 요소가 연결된 시스템이다.

- **모델**은 현재 정보로 다음 행동을 선택한다.
- **컨텍스트**는 사용자 요청, 이전 행동, 도구 결과를 담는다.
- **도구**는 주문 조회처럼 외부 환경을 읽거나 바꾼다.

모델은 도구를 직접 실행하지 않는다. 모델은 “이 도구를 이 인수로 호출하라”는 구조화된 요청을 만든다. 애플리케이션 코드가 요청을 검사하고 도구를 실행한 뒤, 결과를 새 관찰로 모델에 돌려준다.

반드시 기억할 문장은 이것이다.

> 모델은 행동을 제안하고, 코드는 실행하며, 환경의 결과가 다음 판단의 근거가 된다.

## 네 가지 역할로 기록하기

실행 기록은 하나의 긴 문자열보다 역할이 구분된 메시지 목록으로 관리한다.

- `system`은 에이전트의 책임과 금지 조건을 정한다.
- `user`는 사용자의 요청과 추가 설명을 담는다.
- `assistant`는 모델의 답변 또는 도구 호출 요청을 담는다.
- `tool`은 코드가 실제 도구를 실행해 얻은 결과를 담는다.

이 구분이 없으면 모델의 제안과 환경에서 확인된 사실이 뒤섞인다. 예를 들어 `assistant` 메시지의 “환불 가능”은 아직 판단일 수 있지만, `tool` 메시지의 주문 상태는 조회 시스템이 반환한 관찰이다. 둘을 같은 신뢰도로 다루면 에이전트가 자신의 추측을 사실처럼 재사용할 수 있다.

## 한 바퀴가 아니라 반복 루프

에이전트는 보통 다음 순서를 반복한다.

1. 사용자 요청과 지금까지의 기록을 본다.
2. 답변할지 도구를 요청할지 결정한다.
3. 코드가 허용된 도구만 실행한다.
4. 도구 결과를 컨텍스트에 추가한다.
5. 목표를 달성했거나 더 진행할 수 없으면 멈춘다.

이 패턴을 ReAct 루프라고도 한다. 여기서는 이름보다 책임 분리가 중요하다. 모델의 출력은 아직 제안이며, 도구 결과가 실제 관찰이다.

```python
messages = [user_request]

for step in range(MAX_STEPS):
    decision = model.choose(messages, tools)
    if decision.kind == "final":
        return decision.text

    result = run_allowed_tool(
        decision.tool,
        decision.arguments,
    )
    messages.append(decision)
    messages.append(result)

raise StepLimitExceeded()
```

`MAX_STEPS`는 단순한 편의 기능이 아니다. 도구가 계속 실패하거나 모델이 같은 조회를 반복할 때 루프를 끝내는 안전장치다. 프로덕션 시스템은 같은 도구와 인수의 반복, 연속 오류, 시간과 비용 한도도 함께 확인한다.

## 워크플로와 자율 판단을 섞기

모든 단계를 모델이 정해야 에이전트인 것은 아니다. 순서가 명확하고 어기면 위험한 단계는 코드로 고정한다. 여러 주문 중 어떤 주문을 더 확인할지처럼 상황마다 경로가 달라지는 단계만 모델이 선택하게 한다.

Mori Shop에서는 “주문 조회 → 사유 확인” 사이의 탐색을 모델에 맡길 수 있다. 그러나 뒤에서 추가할 “견적 → 사용자 확인 → 환불 생성 → 상태 재조회” 순서는 고정한다. 이 혼합 방식은 자율 판단이 필요한 곳을 남기면서도 중요한 절차가 생략되는 일을 막는다.

## Mori Shop 최소 에이전트

이번 단계에서 허용하는 도구는 두 개뿐이다.

- `find_orders(customer_id, date_range)`: 기간 안의 주문 후보를 찾는다.
- `get_order(order_id)`: 상품, 금액, 배송일, 상태를 읽는다.

두 도구는 외부 상태를 바꾸지 않는다. 에이전트의 첫 성공 조건도 작게 잡는다.

1. 고객과 기간에 맞는 주문을 찾는다.
2. 블루투스 이어폰이 포함된 주문 `O-1042`를 확인한다.
3. 환불 사유가 없다는 사실을 발견한다.
4. 사유를 질문하고 실행을 멈춘다.

주문을 찾았다고 해서 환불이 끝난 것은 아니다. 이 시점에 검증된 것은 “어떤 주문인지”뿐이다. 정책, 금액, 사용자 확인, 실제 환불 상태는 뒤 모듈에서 차례로 추가한다.

## 변경 전후 비교

변경 전 챗봇은 사용자 문장만 보고 환불 완료를 선언했다. 변경 후 에이전트는 주문 시스템에서 대상을 확인하고, 부족한 사유를 질문했다. 더 많은 일을 한 것이 아니라 **확인되지 않은 일을 하지 않은 것**이 핵심 개선이다.

이 차이는 최종 문장만 읽으면 놓치기 쉽다. 실행 궤적에는 어떤 도구가 어떤 인수로 호출되었는지, 무엇을 반환했는지, 실제 상태가 바뀌었는지가 남아야 한다. 이후 평가에서는 답변과 궤적을 함께 검사한다.

## 새 상황에 적용하기

다음 세 경우에는 종료 조건이 달라진다.

- 주문이 없으면 기간이나 계정을 다시 확인하도록 요청한다.
- 주문이 여러 개면 상품명이나 주문일로 대상을 좁힌다.
- 조회 도구가 연속으로 실패하면 성공한 척하지 않고 중단하거나 사람에게 넘긴다.

반대로 주문이 하나라고 해서 자동 환불해서는 안 된다. “주문을 찾음”은 조회 단계의 완료일 뿐, 전체 환불 업무의 완료가 아니다. 각 단계의 완료 조건을 분리해야 성급한 성공 선언을 막을 수 있다.
