# 0모듈 · 10분 핵심 개요

이 페이지의 목표는 용어를 외우는 것이 아니다. 앞으로 만들 시스템의 전체 지도를 먼저 머릿속에 그리는 것이다.

## 네 문장으로 보는 전체 과정

1. 에이전트는 모델이 도구를 선택하고 결과를 관찰하며 목표를 향해 다음 행동을 정하는 실행 시스템이다.
2. 컨텍스트는 모델이 현재 결정을 내릴 때 사용할 수 있는 정보다.
3. 하네스는 모델의 결정을 제약하고 검증하며 실패에서 복구시키는 코드다.
4. 평가는 변경된 시스템이 실제로 더 나아졌는지를 판단하는 기준이다.

이 네 요소는 순서대로 쌓인다. 실행 루프가 없으면 에이전트가 아니며, 올바른 컨텍스트가 없으면 모델은 잘못 판단한다. 안전한 하네스가 없으면 한 번의 오판이 실제 사고로 이어질 수 있다. 평가가 없으면 수정이 개선인지 우연인지 알 수 없다.

## 챗봇, 워크플로, 에이전트

| 형태 | 다음 단계를 정하는 주체 | 알맞은 상황 |
| --- | --- | --- |
| 챗봇 | 사용자가 새 질문을 보낸다 | 설명, 요약, 초안 작성 |
| 워크플로 | 개발자가 미리 정한 순서가 정한다 | 순서와 규칙이 안정적인 업무 |
| 에이전트 | 모델이 관찰 결과를 보고 정한다 | 경로를 미리 모두 알 수 없는 업무 |

세 형태는 우열 관계가 아니다. 환불 전에 반드시 사용자 확인을 받아야 한다면 그 순서는 워크플로로 고정하는 편이 안전하다. 반면 주문이 여러 개일 때 어떤 추가 정보를 물을지는 에이전트가 상황에 맞게 결정할 수 있다. 실제 시스템은 보통 둘을 섞는다.

## Mori Shop에서 벌어진 일

고객 `C-102`가 다음과 같이 요청했다.

> 지난주 받은 블루투스 이어폰을 환불해 줘.

주문 번호는 `O-1042`, 결제 금액은 89,000원이다. 상품은 5일 전에 배송되었지만 첫 요청에는 환불 사유가 없다. 단순 변심인지 제품 결함인지에 따라 적용 정책이 달라지므로 곧바로 환불하면 안 된다.

과정이 끝날 때 Mori Shop 에이전트는 대상 주문과 사유를 확인하고, 시행 중인 정책을 찾고, 환불액을 계산한다. 사용자에게 대상과 금액을 다시 확인받은 뒤에만 환불을 한 번 생성한다. 마지막에는 실제 환불 상태를 조회한 뒤 결과를 보고한다.

## 여섯 모듈의 연결

- 1모듈은 주문을 조회하고 부족한 정보를 묻는 최소 실행 루프를 만든다.
- 2모듈은 정책과 작업 상태를 올바른 컨텍스트로 구성한다.
- 3모듈은 읽기·견적·실행 도구의 책임과 위험을 나눈다.
- 4모듈은 확인, 멱등성, 재시도, 사후 검증으로 사고를 막는다.
- 5모듈은 정상·경계·실패 상황을 포함한 평가 세트를 만든다.
- 6모듈은 실패 원인에 맞춰 지식, 지침, 코드 중 수정 위치를 고른다.

각 모듈은 앞선 결과물을 버리지 않고 개선한다. 모든 필수 시나리오는 로컬 데이터만 사용하므로 실제 환불이나 외부 API 호출은 일어나지 않는다.
