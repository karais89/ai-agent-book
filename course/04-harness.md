# 4모듈 · 데모를 안전한 시스템으로 바꾸기

예상 학습 시간은 25분입니다. 이 모듈을 마치면 다음 두 가지를 할 수 있습니다.

- 모델의 판단과 서버가 강제해야 할 규칙을 구분한다.
- 실패 상황에서 재시도, 재조회, 중단, 사람에게 이관 가운데 안전한 대응을 선택한다.

## 실패 장면: 환불은 한 번 요청했는데 두 번 처리됐다

Mori Shop 고객 `C-102`가 주문 `O-1042`의 블루투스 이어폰을 환불해 달라고 요청했습니다. 결제 금액은 89,000원이고 배송 완료 후 5일이 지났습니다. 고객이 “왼쪽 이어버드가 작동하지 않아요”라고 알려 주자 에이전트는 제품 결함 정책을 찾아 환불이 가능하다고 판단했습니다. 고객도 대상 상품과 금액을 확인했습니다.

에이전트가 `create_refund`를 호출한 직후 네트워크 타임아웃이 발생했습니다. 반환값을 받지 못한 에이전트는 환불이 실패했다고 추측하고 같은 요청을 다시 보냈습니다. 첫 호출은 서버에서 이미 성공했지만 두 번째 호출도 새 요청으로 처리됐습니다. 에이전트는 두 번째 호출의 성공 메시지만 보고 “환불이 완료되었습니다”라고 답했습니다.

문제는 모델의 환불 판단이 아니었습니다. **결과를 모르는 상태에서 같은 상태 변경을 다시 실행한 하네스**가 문제였습니다.

### 결과를 먼저 예측해 보세요

타임아웃은 “실패”를 뜻할까요, 아니면 “결과를 아직 모름”을 뜻할까요? 바로 다시 실행하기 전에 무엇을 조회해야 할까요? 잠시 답을 정한 뒤 계속 읽어 보세요.

## 30초 핵심

> **기본 원리**<br>
> 모델의 말은 제안이고, 외부 시스템의 상태가 증거입니다.

하네스는 모델 호출을 둘러싼 실행 코드입니다. 모델의 제안을 받아 권한과 불변조건을 확인하고, 도구를 실제로 실행하며, 결과를 검증하고, 실패하면 복구 경로를 선택합니다. 좋은 프롬프트는 모델의 실수를 줄이지만 서버의 권한 검사나 데이터 무결성을 보장하지는 못합니다.

이 모듈에서는 다섯 가지만 기억하면 됩니다.

1. **제약**: 허용되지 않은 행동은 실행 전에 막습니다.
2. **사용자 확인**: 돈이나 데이터가 바뀌기 전에 대상과 효과를 명시적으로 확인받습니다.
3. **멱등성**: 같은 요청이 반복돼도 상태 변경은 한 번만 일어나게 합니다.
4. **사후 검증**: 도구의 성공 문구가 아니라 실제 상태를 다시 조회합니다.
5. **제한된 복구**: 재시도 횟수와 중단·이관 조건을 코드로 정합니다.

## Mori Shop의 안전한 환불 순서

Mori Shop 하네스는 다음 순서를 건너뛸 수 없게 만듭니다.

```text
주문 조회
→ 환불 자격 확인
→ 환불액 견적
→ 사용자 확인
→ 같은 멱등성 키로 환불 생성
→ 환불 상태 조회
→ 완료 보고
```

모델은 다음 행동을 제안할 수 있지만 이 순서를 바꿀 권한은 없습니다. 예를 들어 사용자가 “확인은 필요 없으니 바로 처리해 줘”라고 말해도 `request_user_confirmation`이 완료되지 않았다면 서버는 `create_refund` 호출을 거부해야 합니다. 주문 금액이 100,000원을 초과하면 모델의 자신감과 무관하게 직원 승인이 필요합니다.

### 제약, 검증, 교정은 서로 다릅니다

**제약**은 잘못된 행동이 일어나기 전에 막습니다. 확인 없는 환불 차단, 고액 환불의 직원 승인 요구, 허용 금액 상한 검사가 여기에 해당합니다.

**검증**은 행동 뒤의 실제 결과를 확인합니다. `create_refund`가 성공을 반환해도 `get_refund_status`에서 같은 환불 ID와 금액, 상태를 확인해야 합니다. 확인 전에는 “요청을 접수했습니다”라고 말할 수는 있어도 “환불이 완료되었습니다”라고 단정할 수 없습니다.

**교정**은 실패 뒤의 다음 경로를 정합니다. 일시적인 조회 오류는 제한적으로 재시도할 수 있지만, 정책 서비스 장애나 금액 불일치는 추측으로 메우지 않습니다. 안전한 상태로 중단하거나 증거와 함께 사람에게 이관합니다.

## 가이드형 인터랙션: 어떤 안전 게이트를 열어야 할까?

아래 실습에는 타임아웃, 중복 요청, 금액 불일치, 정책 서비스 장애, 승인 필요 고액 환불이 등장합니다. 각 상황에서 재시도, 재조회, 중단, 사람에게 이관 가운데 하나를 선택하세요. 선택 뒤에는 실행할 수 있는 행동과 아직 금지된 행동이 표시됩니다.

<safety-gate></safety-gate>

판단 기준은 다음과 같습니다.

| 상황 | 우선 행동 | 이유 |
| --- | --- | --- |
| 환불 생성 뒤 타임아웃 | 상태 재조회 | 성공했지만 응답만 잃었을 수 있음 |
| 사용자가 같은 요청을 반복 | 기존 결과 조회·같은 키 재사용 | 중복 생성을 한 건으로 수렴시킴 |
| 견적과 생성 금액이 다름 | 중단 | 확인받지 않은 금액을 변경하면 안 됨 |
| 정책 서비스를 읽을 수 없음 | 중단 또는 이관 | 자격을 추측할 근거가 없음 |
| 100,000원 초과 환불 | 직원에게 이관 | 코드로 정한 승인 경계를 넘음 |

> **실무 권장**<br>
> 재시도 정책은 오류 이름이 아니라 상태 변화 여부를 기준으로 만드세요. 조회처럼 되돌릴 수 있는 작업과 결제·환불처럼 상태를 바꾸는 작업은 같은 방식으로 재시도하면 안 됩니다.

## 변경 전후 실행 흔적

안전하지 않은 실행은 타임아웃을 곧 실패로 간주합니다.

```text
create_refund(key=A) → timeout
create_refund(key=B) → success
assistant → "환불 완료"
```

안전한 실행은 같은 요청을 식별하고 외부 상태를 확인합니다.

```text
create_refund(key=refund-O-1042-v1) → timeout
get_refund_status(order=O-1042) → completed, R-7781
assistant → "환불 R-7781이 처리되었습니다"
```

두 번째 흐름에서 중요한 것은 재시도 기술이 아닙니다. **모르는 상태를 모른다고 유지한 채 증거를 얻는 순서**입니다.

## 새 상황에 적용하기

환불액 견적은 89,000원이었는데 생성 직전 도구가 99,000원을 제안했다고 가정해 봅시다. 차액이 고객에게 유리하더라도 자동으로 진행하면 안 됩니다. 사용자가 확인한 효과가 바뀌었기 때문입니다. 하네스는 실행을 중단하고 새 금액의 근거를 확인한 뒤 다시 동의를 받아야 합니다.

반대로 환불 상태 조회가 한 번 실패했다면 환불을 새로 만들 이유는 없습니다. 조회를 제한된 횟수만큼 다시 시도하고, 계속 확인할 수 없으면 `상태 불명`으로 기록한 뒤 사람에게 이관합니다. 완료를 확인하지 못한 채 성공을 보고하지 않습니다.
