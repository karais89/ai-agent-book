# 3모듈 · 안전하고 이해하기 쉬운 도구

> 예상 시간: 25분 · 2모듈 권장<br>
> Mori Shop 에이전트의 조회·견적·실행 도구를 분리하고, 호출 요청이 실제 환불로 이어지는 과정을 읽는다.

## 학습 목표

이 모듈을 마치면 다음을 할 수 있다.

1. 모델의 도구 호출 요청과 애플리케이션의 실제 도구 실행을 구분한다.
2. 사용 시점, 금지 조건, 입력, 반환값이 분명한 도구를 설계한다.

## 실패 장면: `refund()`는 무엇을 하는가?

초기 Mori Shop 에이전트에는 다음 도구 하나만 있었다.

```text
refund(order_id)
설명: 주문 환불을 처리합니다.
```

고객 `C-102`가 블루투스 이어폰 주문 `O-1042`를 환불해 달라고 하자 모델은 곧바로 `refund("O-1042")`를 요청했다. 이 호출이 환불 가능 여부를 조회하는지, 금액을 계산하는지, 실제 결제를 취소하는지 설명만으로 알 수 없다. 사용자에게 89,000원 환불을 확인받지도 않았는데 외부 상태가 바뀔 수 있다.

### 결과를 예측해 보자

도구 설명에 “환불할 때 사용”이라고 한 줄 더 쓰면 충분할까? 여전히 부족하다. 모델은 사용자의 의도를 해석할 수 있지만, 도구의 숨은 동작이나 서버 규칙을 추측해서는 안 된다. 상태를 읽는 행동과 바꾸는 행동부터 분리해야 한다.

## 30초 핵심

도구는 모델이 외부 세계와 상호작용하는 명시적인 인터페이스다. 모델은 도구를 직접 실행하지 않는다. 모델은 이름과 인수를 담은 호출을 **요청**하고, 에이전트 애플리케이션이 권한과 입력을 검사한 뒤 실행한다. 실행 결과는 다시 모델의 컨텍스트에 들어가 다음 결정을 위한 관찰이 된다.

```text
사용자 요청
→ 모델이 다음 도구 호출을 선택
→ 애플리케이션이 검사하고 실행
→ 도구 결과를 모델에 전달
→ 모델이 다음 행동 또는 종료를 선택
```

이 책임 분리를 지키면 잘못된 호출을 실행 전에 막을 수 있다.

## 조회, 제안, 실행을 분리한다

Mori Shop의 도구는 위험도와 역할에 따라 세 묶음으로 볼 수 있다.

- **조회 도구**는 상태를 읽는다. `find_orders`, `get_order`, `search_refund_policy`, `get_refund_status`가 여기에 속한다. 대체로 되돌릴 외부 변경이 없지만, 개인정보 접근 권한은 여전히 확인해야 한다.
- **제안 도구**는 실행할 내용을 계산한다. `quote_refund`는 환불 가능 여부와 금액을 제안하고, `request_user_confirmation`은 사용자가 대상과 금액을 명시적으로 확인하게 한다.
- **실행 도구**는 외부 상태를 바꾼다. `create_refund`는 실제 환불을 생성한다. 잘못 실행하면 금전 손실이나 중복 처리로 이어질 수 있으므로 가장 엄격하게 다룬다.

하나의 `refund()`에 세 역할을 모두 넣으면 현재 단계를 알기 어렵고 단계별 권한도 적용하기 어렵다. 도구를 나누면 실행 흔적만으로 실패 지점을 찾을 수 있다.

## 좋은 도구 설명은 계약서다

도구 이름만으로 충분하지 않다. 설명에는 다음 네 가지가 보여야 한다.

1. 언제 사용하는가
2. 언제 사용하면 안 되는가
3. 어떤 인수를 받는가
4. 성공과 실패 때 무엇을 반환하는가

상태 변경 도구의 설명을 다음처럼 작성할 수 있다.

```yaml
name: create_refund
use_when: 주문, 정책, 사유, 금액, 사용자 확인이 모두 검증됨
do_not_use_when:
  - 환불 사유가 없음
  - 견적과 확인 금액이 다름
  - 직원 승인이 필요한데 승인되지 않음
arguments:
  order_id: 검증된 주문 ID
  amount: 사용자가 확인한 환불액
  idempotency_key: 중복 생성을 막는 요청 키
returns:
  success: refund_id와 생성 상태
  failure: 오류 코드와 재시도 가능 여부
```

설명은 선택을 돕지만 보안을 보장하지 않는다. 애플리케이션은 같은 조건을 코드로 다시 검사해야 한다. 시스템 프롬프트에 “확인 없이 환불하지 마라”라고 적었다고 결제 권한을 모델에 맡길 수는 없다. 실행 안전장치는 다음 모듈에서 만든다.

## 올바른 도구 루프

고객의 첫 요청에는 주문 번호와 환불 사유가 없다. 에이전트는 다음과 같이 진행할 수 있다.

1. `find_orders(C-102, 지난주)`로 후보 주문을 찾는다.
2. `get_order(O-1042)`로 상품, 금액, 배송일을 확인한다.
3. 환불 사유가 없으므로 사용자에게 질문한다.
4. “왼쪽 이어버드가 작동하지 않아요”라는 답을 받는다.
5. `search_refund_policy(전자제품, 대한민국, 오늘)`로 최신 정책을 가져온다.
6. `quote_refund(O-1042, 제품 결함)`으로 89,000원 견적을 계산한다.
7. `request_user_confirmation`으로 주문과 금액을 보여 주고 확인받는다.
8. 확인 뒤에만 `create_refund`를 요청한다.
9. 반환된 환불 ID로 `get_refund_status`를 호출해 실제 상태를 확인한다.

모델은 매 단계에서 도구 결과를 관찰하고 다음 행동을 새로 결정한다. 도구가 실패했는데 성공했다고 가정하거나, 반환되지 않은 값을 만들어 다음 호출에 넣어서는 안 된다.

## 변경 전후 실행 흔적

### 변경 전

```text
모델 요청: refund("O-1042")
애플리케이션 실행: 의미가 모호한 단일 도구 호출
도구 결과: "처리됨"
문제: 정책·금액·확인·실제 상태를 검증할 수 없음
```

### 변경 후

```text
모델 요청: quote_refund("O-1042", "제품 결함")
도구 결과: eligible=true, amount=89000
다음 행동: 사용자에게 주문·금액 확인 요청
확인 뒤 실행: create_refund(...), get_refund_status(...)
결과: 각 단계의 근거와 외부 상태를 추적할 수 있음
```

호출 수는 늘어나지만 읽기와 쓰기의 경계가 생긴다. 금액 계산, 실행 승인, 실제 상태 확인 시점도 추적할 수 있다.

## 고장 주입: 견적 결과가 예상과 다르다

`quote_refund`가 89,000원이 아니라 79,000원을 반환했다고 가정하자. 모델이 “아마 배송비 때문일 것”이라고 추측해 계속 진행하면 안 된다. 도구 결과에 공제 사유가 없다면 필요한 정보가 부족한 것이다. 입력한 주문과 사유가 맞는지 확인하고, 도구의 오류 또는 정책 결과를 다시 조회해야 한다.

시간 초과가 곧 실패를 뜻하지는 않는다. 서버에서 이미 처리가 끝났을 수도 있다. 상태 변경 요청을 무작정 반복하면 중복 환불이 생긴다. 지금은 “결과를 관찰하지 못했으므로 완료라고 말하지 않는다”는 원칙만 기억하자. 안전한 재시도는 4모듈에서 다룬다.

## 도구가 많을수록 좋은가?

도구가 많으면 겹치는 설명도 늘어난다. `refund_order`, `cancel_payment`, `issue_credit`, `return_item`의 설명이 비슷하면 올바른 도구를 고르기 어렵다. 자주 쓰는 최소 도구부터 제공하고 책임이 겹치지 않게 설계하자.

기준은 개수가 아니라 경계의 명확성이다. 읽기 작업은 작고 단순하게 유지하고, 상태 변경은 별도 도구로 분리해 더 강한 검사를 적용한다.

## 꼭 기억할 문장

> 모델은 도구 실행자가 아니라 호출 제안자이며, 실제 실행과 권한 검사는 애플리케이션의 책임이다.
