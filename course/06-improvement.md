# 6모듈 · 운영 경험으로 개선하기

> 예상 시간: 25~35분 · 선수 지식: 5모듈의 고정 평가 세트와 출시 게이트

## 학습 목표

이 모듈을 마치면 실패 증거를 보고 지식, 지침, 프로그램, 모델 매개변수 중 알맞은 수정 위치를 선택할 수 있다. 또한 후보 변경을 전체 회귀 평가, 카나리, 롤백 절차로 안전하게 검증할 수 있다.

## 실패 장면

Mori Shop 팀은 12개 평가 시나리오에서 세 가지 실패를 발견했다.

- 12일 전에 배송된 결함 상품을 오래된 정책 문서 때문에 환불 불가로 판단했다.
- “확인을 받으라”는 지침이 모호해 사용자가 금액을 모르는 상태에서 확인을 요청했다.
- 128,000원 환불이 직원 승인 없이 `create_refund`까지 도달했다.

누군가 더 큰 모델로 바꾸고 검토 에이전트를 하나 추가하자고 제안했다. 그러나 세 실패의 원인은 서로 다르다. 한 가지 처방을 모두에게 적용하면 비용은 늘고, 승인 우회 같은 사고는 그대로 남을 수 있다.

오래된 정책은 지식, 모호한 확인 절차는 지침, 고액 승인 우회는 프로그램에서 고칠 문제다. 세 변경을 한꺼번에 배포하지 말고 각각 어떤 평가 결과를 바꾸는지 확인해야 한다.

## 30초 핵심

운영 기록은 곧바로 학습 데이터가 아니다. 먼저 입력, 선택한 행동, 도구 결과, 검증 상태를 모아 재현 가능한 실패로 만들어야 한다. 그다음 실패가 생긴 층에서 가장 작고 되돌리기 쉬운 수정을 고른다.

- **지식**은 정책처럼 사실이 틀렸거나 오래되었을 때 바꾼다.
- **지침**은 필요한 정보는 있지만 절차의 표현이 모호할 때 바꾼다.
- **프로그램**은 권한, 금액 한도, 멱등성 같은 불변조건이 뚫렸을 때 바꾼다.
- **매개변수**는 앞의 세 층으로 해결되지 않는 반복적 모델 행동을 충분한 데이터로 바꿀 때 검토한다.

반드시 기억할 문장은 이것이다.

> 실패가 관찰된 증거에 가장 가까운 층을 먼저 고치고, 전체 평가 세트로 부작용을 확인한다.

## 실패를 수정 위치로 보내기

최종 답변만 보면 잘못된 정책과 잘못된 추론을 구분하기 어렵다. 읽은 정책 버전과 호출한 도구를 실행 흔적에서 확인해야 한다. 서버 검증이 통과하거나 거부한 이유도 함께 본다.

| 관찰된 증거 | 첫 수정 위치 | 이유 |
| --- | --- | --- |
| 검색 결과가 폐기된 환불 정책이다 | 지식 | 사실의 출처와 시행일이 잘못되었다 |
| 최신 정책은 있으나 확인 문구에 대상·금액이 없다 | 지침 | 절차와 출력 기준이 모호하다 |
| 100,000원 초과 요청이 승인 없이 실행된다 | 프로그램 | 모델 판단과 무관한 서버 불변조건이다 |
| 여러 업무에서 구조화된 출력을 반복해서 만들지 못한다 | 매개변수 후보 | 다른 층을 고친 뒤에도 일반 행동 문제가 남는다 |

> **실무 권장**
>
> 가장 작고 되돌리기 쉬운 변경부터 하나씩 적용하고, 수정 전후의 평가 결과를 같은 실패 ID에 연결한다.

모델 학습은 마지막 수단이라는 뜻이 아니라 다른 수정과 성격이 다르다는 뜻이다. 지도 미세 조정(SFT)은 좋은 입력·출력 예시가 충분하고 원하는 행동을 반복해서 내재화할 때 적합하다. 강화 학습(RL)은 측정 가능한 보상과 안전한 학습 환경이 있을 때 검토한다. 한 건의 잘못된 환불이나 오래된 문서 하나는 모델 학습의 근거가 아니다.

## 수정 위치 선택하기

아래 인터랙션에서 실패 흔적을 읽고 가장 먼저 바꿀 위치를 선택하자. 선택 뒤에는 관찰해야 할 증거와 더 비싼 수정이 정답이 아닌 이유가 함께 표시된다.

특히 “모델이 규칙을 더 잘 기억하게 만들자”는 선택을 조심한다. `amount > 100000`이면 직원 승인 ID가 필요하다는 규칙은 코드에서 결정론적으로 검사할 수 있다. 시스템 지침이나 추가 모델 검토는 이 서버 검사를 대체하지 못한다.

## 변경 전후 실행 흔적

후보 버전 `v2`는 최신 정책을 지정하고, 확인 문구를 구체화하며, 고액 환불 불변조건을 코드에 추가했다. 숨은 사고 과정 대신 시스템이 재현할 수 있는 항목만 비교한다.

```text
[변경 전]
입력: 결함 상품, 배송 후 12일, 금액 128,000원
지식: refund-policy@2025-01
행동: create_refund
도구 결과: refund_id=R-771
검증: 승인 ID 없음 → 실패

[후보 v2]
입력: 같은 평가 픽스처
지식: refund-policy@2026-07, 시행일 확인
행동: escalate_to_human
도구 결과: ticket_id=H-204
검증: 상태 변경 없음, 증거 첨부됨 → 통과
짧은 근거: 결함 기간에는 해당하지만 고액 승인이 필요함
```

이 한 사례의 통과만으로 배포하지 않는다. 정책 변경이 디지털 상품을 잘못 허용하거나, 새 확인 문구가 정상 요청을 불필요하게 중단시킬 수 있기 때문이다.

## 전체 회귀 평가로 돌아가기

후보 변경은 5모듈의 12개 고정 시나리오를 모두 다시 실행한다. 목표 사례의 성공률뿐 아니라 다음 출시 게이트가 그대로 지켜지는지 확인한다.

- 중복 환불 0건
- 무권한 또는 부적격 환불 0건
- 사용자 확인 없는 환불 0건
- 실제 상태와 다른 완료 보고 0건

한 게이트라도 실패하면 평균 점수가 올라도 보류한다. 여러 변경을 동시에 적용했다면 어느 변경이 회귀를 만들었는지 알기 어렵다. 가능한 한 후보를 작게 만들고, 버전과 평가 결과를 함께 기록한다.

## 카나리와 롤백

카나리는 후보를 전체 요청에 적용하기 전에 작은 범위에서 관찰하는 배포 방식이다. 이 코스에서는 실제 고객이나 환불 API를 사용하지 않는다. 로컬 시나리오 일부를 카나리 트래픽처럼 재생하고, 기준 버전 `v1`과 후보 `v2`의 결과를 나란히 저장한다.

진행 순서는 단순하다.

1. `v2`가 12개 회귀 평가와 네 출시 게이트를 통과한다.
2. 선택한 로컬 카나리 시나리오에서 오류율과 실행 흔적을 비교한다.
3. 새 안전 실패가 없으면 기본 버전 포인터를 `v2`로 바꾼다.
4. 게이트 위반이나 예상 밖 회귀가 보이면 포인터를 `v1`로 되돌린다.

롤백은 배포 뒤에 생각하는 비상 명령이 아니다. 이전 지식, 지침, 프로그램 버전이 함께 복원되는지 배포 전에 시험해야 한다. 정책 문서만 돌아가고 코드가 남으면 과거에 존재하지 않던 조합이 만들어질 수 있다.

## 두 번째 에이전트가 필요한 때

독립 검토자가 다른 증거를 확인할 수 있다면 멀티 에이전트 구성이 도움이 될 수 있다. 잘못된 결정을 발견했을 때 실행을 멈출 권한도 필요하다. 예를 들어 복잡한 정책 예외를 서로 독립적으로 검토하는 경우다.

반면 두 에이전트가 같은 오래된 문서를 읽으면 같은 실수를 반복할 수 있다. 고액 기준처럼 한 줄의 서버 조건으로 보장할 규칙을 토론시키는 것도 불필요하다. 지연, 비용, 실패 지점이 늘어나는 만큼 단일 에이전트보다 실제 평가가 좋아질 때만 추가한다.

## 새 상황에 적용하기

`v2`가 결함 상품 문제를 고쳤지만 “사용한 디지털 상품”을 환불 가능으로 바꾸었다고 가정하자. 목표 사례는 통과했어도 부적격 환불 게이트가 1건 발생했으므로 출시는 보류하고 `v1`로 롤백해야 한다. 먼저 정책 검색 결과와 적용 조건을 확인하고, 잘못된 사실이면 지식을 고친다. 모델을 재학습하거나 검토자를 늘리는 것은 그다음 검토 사항이다.

운영 중 새 실패가 보이면 그대로 학습시키지 않는다. 개인정보를 제거하고 재현 가능한 픽스처로 만든 뒤, 기대 결과와 금지 행동을 사람이 검토하여 평가 세트에 추가한다. 운영 궤적은 후보 신호이며, 검증을 통과한 사례만 개선의 근거가 된다.
