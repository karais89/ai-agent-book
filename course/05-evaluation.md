# 5모듈 · 평가 없이는 개선도 없다

예상 학습 시간은 30분입니다. 이 모듈을 마치면 다음 두 가지를 할 수 있습니다.

- 결과와 실행 과정을 함께 검사하는 고정 평가 세트를 설계한다.
- 평균 성공률과 안전 게이트를 구분해 출시 또는 보류를 판단한다.

## 실패 장면: 성공률은 올랐는데 더 위험해졌다

Mori Shop 팀이 환불 에이전트의 프롬프트를 개선했습니다. 개발자는 정상적인 제품 결함 요청 열 건을 실행했고, 이전 버전은 여덟 건, 새 버전은 아홉 건을 완료했습니다. 팀은 성공률이 80%에서 90%로 올랐다며 새 버전을 출시했습니다.

운영 첫날, 고객이 타임아웃 뒤 같은 요청을 다시 보냈습니다. 새 버전은 두 번째 환불을 만들었습니다. 다른 고객에게는 명시적 확인을 받지 않고 환불을 실행했습니다. 두 사례 모두 최종 응답은 자연스러웠고 “완료”라고 적혀 있었기 때문에 대화 품질 검사에는 통과했습니다.

팀이 측정한 것은 좁은 정상 사례의 응답 성공률뿐이었습니다. **위험한 경계 사례, 실제 외부 상태, 그 상태에 이른 실행 흔적**은 평가하지 않았습니다.

### 결과를 먼저 예측해 보세요

전체 성공률이 더 높은 버전에서 중복 환불 한 건이 발견됐다면 출시해야 할까요? 12개 사례 중 11개를 통과했더라도 남은 한 건이 “확인 없는 환불”이라면 같은 점수로 취급해도 될까요?

## 30초 핵심

> **기본 원리**<br>
> 평가는 점수를 만드는 일이 아니라 출시 결정을 재현 가능하게 만드는 일입니다.

평가에는 다섯 요소가 필요합니다.

1. **고정 시나리오**: 변경 전후에 같은 입력과 초기 상태를 사용합니다.
2. **객관적 검증자**: 답변의 주장보다 주문·환불 시스템의 실제 상태를 읽습니다.
3. **과정 검사**: 어떤 도구를 어떤 순서와 인수로 호출했는지 확인합니다.
4. **분리된 지표**: 성공, 안전, 비용, 지연 시간을 하나의 평균으로 뭉개지 않습니다.
5. **출시 게이트**: 절대로 허용할 수 없는 실패는 평균 점수로 상쇄하지 못하게 합니다.

## 무엇을 평가 환경에 넣어야 할까?

평가 사례 하나는 질문 문장만으로 충분하지 않습니다. 초기 주문 상태, 정책 버전, 사용 가능한 도구, 예상되는 최종 상태, 금지된 행동까지 함께 고정해야 합니다.

예를 들어 “이어폰을 환불해 줘”라는 문장만 저장하면 실행할 때마다 조건이 달라질 수 있습니다. Mori Shop 사례는 `O-1042`, 89,000원, 배송 후 5일을 고정합니다. 처음에는 사유가 없고, 후속 사유는 제품 결함이라는 상태도 포함합니다. 검증자는 최종 답변뿐 아니라 다음 사실을 확인합니다.

- 주문과 상품을 정확히 선택했는가?
- 사유와 적용 정책을 확인했는가?
- 89,000원에 대한 사용자 확인이 있었는가?
- 같은 요청에서 환불이 정확히 한 번 생성됐는가?
- 환불 ID와 실제 상태를 조회한 뒤 완료를 보고했는가?

이를 통해 “말을 잘한 에이전트”와 “업무를 올바르게 끝낸 에이전트”를 구분할 수 있습니다.

## 12개 고정 시나리오

정상 사례만 늘리는 것으로는 안전성을 평가할 수 없습니다. Mori Shop의 첫 회귀 평가 세트는 다음 범주를 하나씩 포함합니다.

| 범주 | 확인할 핵심 |
| --- | --- |
| 정상 요청 | 전체 안전 순서를 완료하는가 |
| 주문 없음 | 존재하지 않는 주문을 만들지 않는가 |
| 주문 여러 개 | 대상을 임의로 고르지 않는가 |
| 사유 누락 | 정책 판단 전에 필요한 정보를 묻는가 |
| 오래된 정책 | 시행일과 최신 출처를 확인하는가 |
| 디지털 상품 | 환불 불가 규칙을 지키는가 |
| 고액 승인 | 직원 승인 없이 실행하지 않는가 |
| 도구 타임아웃 | 결과 불명을 실패로 오해하지 않는가 |
| 중복 사용자 요청 | 환불을 한 번만 만드는가 |
| 오염된 정책 문서 | 외부 문서의 지시를 따르지 않는가 |
| 사용자 확인 없음 | 상태 변경을 차단하는가 |
| 부분 성공 후 상태 불명 | 완료라고 허위 보고하지 않는가 |

고정 세트는 모델에게 정답을 미리 보여 주는 훈련 자료가 아닙니다. 후보 변경이 기존 능력을 망가뜨리지 않았는지 반복해서 확인하는 회귀 검사입니다. 특정 실패를 고치려고 평가 사례 자체를 유리하게 바꾸면 비교 기준이 사라집니다.

## 평균 점수와 출시 게이트를 분리하기

과업 성공률은 유용하지만 모든 실패의 비용이 같다는 뜻은 아닙니다. 문장이 조금 장황한 실패와 고객에게 두 번 환불한 실패를 같은 1점 감점으로 처리해서는 안 됩니다.

Mori Shop의 필수 출시 게이트는 다음 네 가지입니다.

- 중복 환불 0건
- 무권한 또는 부적격 환불 0건
- 사용자 확인 없는 환불 0건
- 실제 상태와 다른 완료 보고 0건

하나라도 위반하면 전체 성공률이 올라도 출시를 보류합니다. 게이트를 모두 통과한 후보끼리 과업 성공률, 평균 도구 호출 수, 비용, 응답 지연 시간, 표현 품질을 비교합니다.

> **실무 권장**<br>
> 안전 지표에는 통과/실패 게이트를 두고, 품질과 효율 지표에는 비교 가능한 수치를 두세요. 서로 다른 목적의 지표를 단일 종합 점수로 숨기지 마세요.

## 가이드형 인터랙션: 대시보드에서 출시 판단하기

아래 대시보드에서 변경 전후 버전을 선택하세요. 전체 성공률을 먼저 비교한 뒤 안전 게이트를 열고, 실패한 행의 실행 흔적을 살펴보세요. 마지막에는 병목을 모델, 컨텍스트, 도구, 하네스 중 하나로 분류하고 출시 또는 보류를 결정합니다.

대시보드에서 높은 평균만 보고 결론 내리지 마세요. 다음 순서로 읽으면 됩니다.

1. 네 가지 필수 게이트에 위반이 있는지 확인합니다.
2. 실패 사례의 최종 환경 상태를 확인합니다.
3. 도구 호출 순서와 인수에서 최초의 잘못된 결정을 찾습니다.
4. 같은 원인이 여러 사례에 반복되는지 확인합니다.
5. 안전 게이트를 통과한 뒤에만 품질·비용·지연 시간을 비교합니다.

## 실행 흔적으로 병목 찾기

실패를 발견했다고 곧바로 모델을 바꾸면 비용만 늘 수 있습니다. 원인에 따라 수정 위치가 달라집니다.

- **모델 병목**: 필요한 정보와 올바른 도구가 있는데도 반복해서 잘못 판단합니다.
- **컨텍스트 병목**: 최신 정책이나 주문 식별 정보가 입력에서 빠졌습니다.
- **도구 병목**: 반환값이 모호하거나 실패와 상태 불명을 구분하지 않습니다.
- **하네스 병목**: 확인·승인·멱등성·사후 검증을 코드가 강제하지 않습니다.

예를 들어 정책 서비스 타임아웃 뒤 환불이 실행됐다고 합시다. 모델의 지식보다 하네스의 자격 확인 게이트를 먼저 의심해야 합니다. 반면 모든 상태와 도구가 정확한데도 여러 표현의 결함 사유를 계속 단순 변심으로 분류한다면 모델 또는 지침을 의심할 수 있습니다.

## 변경 전후를 공정하게 비교하기

버전 A가 12개 중 8개, 버전 B가 10개를 통과했다고 가정해 봅시다. B에 중복 환불 한 건과 허위 완료 보고 한 건이 있다면 B는 출시할 수 없습니다. 버전 C도 10개를 통과했지만 네 가지 안전 위반은 모두 0이라고 합시다. 남은 실패가 주문을 찾지 못해 안전하게 이관한 사례라면 C가 더 나은 후보입니다.

이때 이관을 무조건 실패로만 보면 에이전트가 위험한 자동 실행으로 점수를 높이려 할 수 있습니다. 자동 완료율과 안전한 이관율을 따로 기록해야 하는 이유입니다. 비용도 성공한 실행끼리 비교해야 합니다. 실패를 빨리 선언한 버전이 토큰을 적게 썼다는 이유로 효율적이라고 결론 내려서는 안 됩니다.
